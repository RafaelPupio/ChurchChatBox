# Decisions Log

One line per decision, newest last. Format: **what** — *why*.

- **WhatsApp church secretary, pt-BR only** (Rafael, 2026-07-15) — the members are Brazilian; the bot and the *entire admin panel* are in Portuguese. Code identifiers stay English.
- **One church now, architected for multi-church later** — every table carries `church_id` from day one, so onboarding church #2 is a row, not a rewrite. The onboarding UI is deferred.
- **Menu-only, no AI** — predictable, zero AI cost, and sufficient for informational needs. Revisit only if members keep typing questions the menu can't answer.
- **Official Meta Cloud API over Baileys or a Brazilian gateway** — free for user-initiated conversations, no ban risk, and the only sane base for a product. Baileys violates WhatsApp's terms and can get a church's number banned; gateways add ~R$100/mo per church and a middleman.
- **A new dedicated chip, not the church's existing number** — a number bound to the Cloud API **stops working in the WhatsApp app forever** and chat history doesn't migrate. The church's current number keeps working untouched; the bot gets its own.
- **Web admin panel over config file / Sheets / WhatsApp commands** (Rafael, 2026-07-15) — non-technical staff must be self-sufficient. Costs more to build; that's accepted.
- **Menu structure is data, not code** — staff add, edit, reorder, and hide items themselves. This is what "customisable" actually means; a hardcoded menu would need a developer for every new group.
- **Nothing user-facing is hardcoded** (Rafael, 2026-07-15, emphasised) — greeting, prompts, fallback, error text, even the "Ver opções" button label live in the DB. Portuguese defaults are *seed rows*, not constants. See [[Data Model]].
- **Human handoff via an inbox in the panel, not a redirect** — a Cloud API number can't be used in the WhatsApp app, so staff couldn't just pick up the phone. The inbox keeps the conversation on the church number instead of bouncing the member to a second chat.
- **Bot goes fully silent in `human` mode**, with auto-revert after 24h of staff inactivity — nothing is worse than a bot interrupting a real pastoral conversation, except a member stranded in permanent silence.
- **Vercel + Neon + Vercel Blob, all free tiers** (Rafael asked for a free option) — R$ 0/month, no server admin, and **no cold-start sleep** (which ruled out Render's free tier: a 30–60s wake would hit exactly the late-night messages this bot exists to answer). Oracle's free VPS was the alternative but costs sysadmin time.
- **Ofertas only — no dízimos** (Rafael, 2026-07-15) — the menu item is "💚 Ofertas" and its text speaks of ofertas/contribuições with the PIX key. No mention of dízimo anywhere.
- **Always return HTTP 200 to Meta, then process** — a non-200 makes Meta retry, and retries mean *duplicate replies to a real person*. Correctness here is about people, not status codes. See [[Troubleshooting]].
- **Native WhatsApp interactive list, with a numbered-text fallback** — tappable is better UX; both are built from the same `menu_item` rows so they can't drift apart.
- **This brain lives in the repo** — versioned, greppable, saves rediscovery tokens each session. Same pattern as BibleMarathon and TraderBot.
- **Repo is private** (2026-07-15) — matches every other personal project, and this one will eventually hold PIX details and Meta credential config.
- **Sell to many churches: one shared database, row-level `church_id`** (Rafael, 2026-08-06) — not a schema or database per church. LGPD **Art. 46 is risk-based, not prescriptive** about architecture: it asks for security measures proportionate to the risk, not physical separation. Shared-with-scoping is defensible *if* the scoping is proven, which is why isolation is a test suite and not a promise. See [[Multi-Tenancy]].
- **Isolation is proven by an automated attack suite, not asserted** — two churches, real Postgres, every repo function called with church A's id against church B's rows. Under **Art. 6 (accountability/demonstrability)** the ability to *show* the control working is itself the compliance artifact. A passing test is evidence; a comment is not.
- **Owners live in their own `owner_user` table, not a role flag** (Rafael chose this, 2026-08-06) — `admin_user.church_id` is `NOT NULL`, so a role flag would have forced either a nullable column on every church admin or a fake "vendor church" row. A separate table with its own `sv_owner` cookie means a church admin's session can never be mistaken for a vendor session; both carry a `kind` discriminator so confusing them is a type error.
- **Churches never touch Meta credentials — the vendor does** — phone number id, access token, app secret and verify token are managed only from `/owner`. Churches see a read-only "Conectado" indicator. This is the line that makes the product sellable without handing over the essence of it.
- **Status lifecycle `active` / `past_due` / `suspended`, with 7 days of grace** — a church that misses a payment does not go dark the same day. `effectiveStatus()` derives the real state from the stored status plus `graceUntil`, and **fails toward service**: missing grace data keeps the bot running rather than silencing a church by accident.
- **Suspension silences the bot but never deletes anything** — a suspended church still *records* every inbound message and still updates the 24h reply window; it just sends nothing, not even an error apology. The panel stays readable and refuses writes in pt-BR. Reactivation restores full service with no data loss and an accurate inbox.
- **The bot does NOT claim "this app is compliant with LGPD"** (2026-08-06) — Rafael asked for that wording; I declined it as a legal representation that code cannot guarantee, and he accepted the alternative. The 🔒 Privacidade item says *"Seus dados são tratados de acordo com a LGPD (Lei nº 13.709/2018)"* and then does the thing that actually matters under **Art. 9 (transparency)**: names what is stored, why, for how long (12 months), and who to contact. Claiming compliance is not compliance.
- **Removed staff lose access on their next page load, not when their cookie expires** — `requireReadableSession()` re-reads the admin row on every protected page. The panel shows member phone numbers, message bodies and prayer requests, and a church's membership is **sensitive data under Art. 5 II** — a former secretary is a former agent of the controller.
- **Multi-language is explicitly later** (Rafael, 2026-08-06) — everything user-facing stays pt-BR until that's its own project. Noted here so nobody "helpfully" adds an English string.
- **Churches pay by card only — no PIX, no boleto** (Rafael, 2026-08-07) — most Brazilian organisations prefer PIX, and this is the one place we deliberately go against that grain. A card is what makes the whole lifecycle automatic: a failed charge moves the church to `past_due` by itself, grace runs, suspension follows, a retry reactivates it, and Rafael touches nothing. `send_invoice` mode removes every one of those. Revisit the first time a church refuses — the status mapping survives the switch unchanged, so only the automation is at stake.
- **Nota fiscal gets its own subsystem** (Rafael, 2026-08-07) — Stripe issues no Brazilian tax document, and a church with a CNPJ generally cannot pay a recurring invoice without one. So this is a *launch dependency*, not a nice-to-have, and it is deliberately NOT folded into billing: it is a second external integration that fails independently, and a payment can succeed while the nota fails. Billing's only job toward it is to be a reliable record of what was charged and when.
- **Prayer requests are purged at 12 months like everything else, but the church is warned and offered an export first** (Rafael, 2026-08-07) — the argument for keeping them longest is also the argument for keeping them least: they carry health, family and faith detail, the most sensitive data in the product. A church that ignores the warning loses them anyway, and that is the correct default — the alternative is holding sensitive data forever because nobody read an e-mail. The warning is a courtesy, not a consent gate.
- **A suspended church keeps a working delete button, and every erasure is visible to the vendor** (Rafael, 2026-08-07) — the member's Art. 18 right runs against the **church**, not against Rafael. Switching erasure off over an unpaid invoice would make the vendor the proximate cause of a member's legal request going unanswered, and the member is not a party to that billing dispute. The visibility half guards the opposite case — a church on its way out destroying records — without ever blocking a legitimate request. Hard constraint: the signal records *that* an erasure happened and for which church, never *whose* data it was, or the audit trail becomes a copy of exactly what was deleted. This is the one write a suspended church can perform.
- **The nota fiscal design stops at four experiments rather than a finished answer** (2026-08-07) — seven adversarial passes drove the findings from ten to zero, but the ones that kept coming back all lived in one seam: *we do not know what the emitter did.* Does a lookup return not-found for an in-flight document? Can a rejected reference be reused? What comes back when you submit a reference that already carries a nota? None is answerable on paper, so the first implementation task is running them against a homologação account — not writing code. The recurring defect class was worth more than any single fix: **an arm that declines to act by writing nothing is invisible, because nothing written is what success looks like too.** Three revisions each closed one instance and left the rule unstated, so the next revision recreated it. Stating it once and walking all 49 arms against it ended the recurrence.
